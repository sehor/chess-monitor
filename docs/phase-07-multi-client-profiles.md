# 阶段 7：多客户端 Profile

## 目标

在不分叉核心跟踪算法的前提下扩展到多个桌面或网页象棋客户端、不同主题、屏幕区域模式和棋盘方向。新增客户端应主要通过 Profile、模型资源和少量声明式适配规则完成。

本阶段不承诺“任意未知客户端自动识别”；每个支持项都必须有明确的客户端版本、主题、DPI 和验收矩阵。

## 工具选择

- Profile Manager + SQLite：多 Profile、版本、兼容范围和优先级。
- Vue 3：Profile 列表、自动匹配解释、校准、测试、复制和编辑界面。
- JSON 导入导出 + schema 校验：共享 Profile；外部输入视为不可信数据。
- 模型资源清单：按客户端/主题绑定 ONNX 模型或声明共用模型。
- 回放框架：为每个 Profile 运行同一套核心跟踪验收。
- 可选屏幕区域捕获：窗口不可枚举时使用，但必须明确移动和遮挡限制。

## 技术路线

1. 扩展 Profile schema：客户端名称/版本、窗口规则、棋盘坐标、主题、方向、DPI 范围、变化阈值、动画规则、模型、资源哈希和兼容版本。
2. 自动匹配返回候选和原因，由用户确认首次绑定；不得仅凭窗口标题的宽泛子串自动连接。
3. Profile 编辑器提供实时 90 点覆盖层、ROI 预览、静态噪声采样、走子样本测试和阈值建议。
4. 导入时进行 schema、版本、范围、路径和哈希校验；禁止导入包执行代码或引用任意外部可执行文件。
5. 新客户端接入先走数据化流程：采集 → 校准 → 阈值基准 → 模型验证 → 回放 → 实时整盘测试。只有证据表明现有字段不足时才修改核心代码。
6. 为客户端特例建立受限、声明式规则；若必须新增代码适配器，应有独立接口、测试和所有既有 Profile 的回归报告。
7. Profile 与模型独立版本化，旧棋局保留当时使用的版本信息，便于诊断。
8. 支持 Profile 导出、导入、复制、禁用和回滚到上一可用版本。

## 交付物

- 多 Profile 管理和可视化编辑器。
- 安全的 Profile 导入导出格式与迁移机制。
- 至少两个新增客户端或主题的已验证 Profile。
- 按客户端/主题/DPI 组织的兼容矩阵和回放报告。
- 新客户端接入清单与模板。

## 验收标准

- 在首个客户端之外，至少新增两个不同客户端或有显著视觉差异的主题；每个支持项均有不少于 500 个标注着法的回放集。
- 每个 Profile 的静默失步数 = 0，确认着法准确率 ≥ 99.9%，正常样本拒绝率 ≤ 1%。
- 支持矩阵内的 DPI/窗口组合，棋盘定位成功率 ≥ 99%。
- Profile 导入导出往返后语义一致；损坏、过新版本、路径越界或哈希不符的文件全部被安全拒绝。
- 窗口匹配到多个候选时错误自动连接次数 = 0。
- 新增 Profile 后，阶段 3–6 的全部既有回放回归继续通过。
- 至少一个新增客户端仅通过 Profile/资源完成接入，不修改 Board Tracker 核心算法；若无法做到，必须有记录充分的接口缺口说明。
