# 阶段 3：轻量实时走子跟踪

## 目标

完成项目最重要的能力：在已知上一局面的前提下，通过 90 个交叉点 ROI 的图像变化和合法走法集合推导实际走子。正常对局不运行完整棋子分类模型。

系统的安全原则是“宁可拒绝或暂停，也不能静默确认错误着法”。

## 工具选择

- Window Capture + Profile Manager：提供带时间戳、尺寸和有效性状态的棋盘帧。
- `sharp` + TypedArray：ROI 归一化和变化分数。
- `@west-shell/xiangqi.js` 适配层：根据上一 Position 和行棋方枚举合法着法。
- TypeScript 状态机：显式管理抓屏、动画、候选、确认和失步。
- Vitest：纯函数、候选匹配和状态迁移测试。
- 离线帧序列回放器：使用标注棋谱做确定性回归，不依赖实时客户端。

## 技术路线

1. 状态机至少包含 `NO_BOARD`、`CALIBRATING`、`STABLE`、`MOVE_ANIMATING`、`MOVE_CANDIDATE`、`MOVE_CONFIRMED`、`DESYNC` 和 `RESCANNING`。
2. 只有捕获源有效、Profile 未过期、画面连续稳定若干帧时，才从 `STABLE` 开始判断走子。
3. 对 90 点计算相对基线的变化分数。动画期间累积候选，不提交中间帧；画面稳定后形成观察变化集和每点置信度。
4. 从上一 Position 枚举全部合法走法，并预测每步应影响的起点和终点。普通走子和吃子都至少改变两个 ROI，最终以变化集合、变化强度、时序和合法性综合评分。
5. 只有一个候选超过确认阈值且与次优候选拉开安全差距时才提交 `MOVE_CONFIRMED`；候选不唯一、帧缺失、坐标失效或变化异常时拒绝确认。
6. 确认后原子更新 Position、行棋方、FEN、棋谱和新的图像基线。任何一步持久化失败不得让内存局面与 UI 显示不一致。
7. 检测无法由单步合法走法解释的变化、连续超时或局面跳转，进入 `DESYNC` 并停止向引擎提供新局面。
8. MVP 提供手动选择候选、撤销最近确认和从标准初始局面重新开始；自动全盘识别留到阶段 5。
9. 所有决策写入结构化事件：输入帧、状态迁移、变化点、候选列表、分数、确认/拒绝原因和 Position 哈希。

## 交付物

- Board Tracker、状态机和合法走法候选匹配器。
- 稳定帧、动画等待和变化集生成模块。
- 标注帧序列离线回放器。
- 手动候选确认、暂停和重新同步入口。
- 跟踪事件与失败样本导出。

## 验收标准

固定客户端、主题和已验证 Profile 下，使用不少于 1,000 个标注着法的离线回放集，并至少实时完整跟踪 10 盘棋：

- 静默失步数 = 0。
- 确认着法准确率 ≥ 99.9%；任何错误不得被吞掉或继续作为正常局面分析。
- 实际起点和终点变化点召回率 ≥ 99%。
- 正常样本拒绝率 ≤ 1%；被拒绝样本全部进入明确候选或 DESYNC 状态。
- 画面稳定到 `MOVE_CONFIRMED` 的延迟 P95 < 500 ms（在阶段 0 记录的测试机和默认抓帧率上）。
- 人为删除帧、插入动画中间帧、改变高亮或模拟窗口捕获失败时，系统不会提交无法由合法单步解释的着法。
- 从标准开局完整跟踪到结束时，最终 FEN 和标注棋谱一致。
