# 阶段 5：完整棋盘识别与失步恢复

## 目标

为“上一局面未知”或轻量跟踪已经失步的场景提供完整棋盘识别：从 90 个交叉点 ROI 推断 15 类状态（空位、红黑各 7 类棋子），经置信度和象棋规则校验后重建 Position，并安全返回轻量实时跟踪。

完整识别只在首次中盘连接、未知残局导入、手动重同步和 `DESYNC` 时运行，不替代阶段 3 的正常跟踪。

## 工具选择

- `xiangqi-bot`：作为识别核心的初始代码基础，优先复用 ONNX 分类、ROI 预处理、校准、双帧概率融合、方向判断、棋子数量检查和 FEN 生成思路；macOS 截图部分不移植。
- Python + ONNX Runtime：本阶段优先用于快速验证现有模型和数据处理链路。
- PyTorch：仅在模型实测不足时用于开发环境的数据增广、微调或重训，并导出 ONNX。
- `@west-shell/xiangqi.js` 适配层：FEN 基础合法性、行棋方和候选局面校验。
- 标注工具与版本化数据集：保存 ROI 类别、原始截图、客户端/主题/DPI 和训练/验证/测试划分。
- Recognition Worker：独立进程或受控工作进程，避免推理阻塞 Electron 主进程。

## 技术路线

1. 固定目标客户端、主题和 Profile，先用独立测试集验证 `xiangqi-bot` 现有 ONNX 模型，不预设模型可直接通用。
2. 复现模型要求的 ROI 尺寸、颜色空间、归一化和类别顺序，并为模型文件建立哈希、版本和类别映射清单。
3. 从一到多张稳定帧裁剪 90 个 ROI，运行批量 ONNX 推理，保留每点 Top-k 概率而非只保留最终标签。
4. 通过多帧概率融合、红黑方向、将帅数量、棋子数量上界、位置规则和 FEN 校验生成一个或多个候选局面。
5. 只有候选唯一且整盘置信度达到门槛时才接受；不确定时展示低置信度交叉点，允许用户修正，禁止“猜一个最可能局面”后静默继续。
6. 现有模型不足时，按客户端/主题分层收集数据，严格按对局或截图来源切分训练、验证、测试集，避免同一帧的相邻裁剪泄漏到不同集合。
7. 需要训练时在开发环境使用 PyTorch，导出 ONNX 后做数值一致性、类别映射、速度和准确率验证；发行资源只包含 ONNX 和推理运行时。
8. 重同步采用两阶段提交：识别候选 → 规则与用户校验 → 原子替换 Position → 重建图像基线 → 返回 `STABLE`。失败则保持 `DESYNC`。
9. Recognition Worker 超时、崩溃或模型损坏时返回结构化错误，并可安全重启；不得拖死 Electron 主进程。

## 交付物

- 目标客户端模型基准报告和“复用/微调/重训”决策。
- Recognition Worker 与版本化模型资源清单。
- 全盘识别、低置信度修正和重同步流程。
- 独立测试集、标注规范、失败样本和指标报告。
- 若发生训练：可重复训练/导出说明及 ONNX 一致性报告。

## 验收标准

在固定客户端、主题和三个 DPI 档位的独立测试集上，至少包含 300 张从未用于调参或训练的完整棋盘截图，其中残局、中盘、翻转方向和不同棋子密度均有覆盖：

- 单个交叉点分类准确率 ≥ 99.95%。
- 90 点完整布局准确率 ≥ 99%。
- 被系统自动接受的局面中，错误接受数 = 0；未达置信度门槛的样本必须拒绝或要求修正。
- 人为触发至少 100 次 DESYNC，重同步成功率 ≥ 99%，成功重同步后的 FEN 与标注一致。
- 从开始重扫到恢复 `STABLE` 的耗时 P95 < 2 s（指定测试机）。
- 模型缺失、哈希不符、类别映射错误、Worker 超时和 Worker 崩溃均能被检测，且不会替换当前可信 Position。
- 最终发行链路不要求用户安装 PyTorch、CUDA 或 Python 开发环境。

## 实现状态（2026-08-19）

代码链路已完成第一版 Stage 05：新增 15 类棋盘识别领域层、最多双稳定帧概率融合、方向映射、棋子数量与位置规则校验、唯一候选与整盘/单点置信度安全门、低置信度点人工修正，以及 Recognition Worker/Coordinator。Worker 在独立 `worker_threads` 线程中执行 ONNX 预处理与推理，主进程只缓存最近两张满足来源/Profile/稳定性条件的帧；模型 manifest 会校验版本、精确类别顺序和 SHA-256，模型缺失、哈希不符、类别映射错误、运行时缺失、超时、崩溃和输出尺寸错误均返回结构化失败。

完整识别已经接入现有实时链路。首次未知局面可以先积累稳定帧、识别并安全启动新棋局；已有棋局（包括 `DESYNC`）则保留当前方向和行棋方，通过“识别候选 → 规则/人工校验 → `RealtimeCoordinator.resync` 持久化 → Recognition 标记已提交 → `FrameAnalyzer.reset` 重建图像基线”的两阶段流程恢复。候选未达到 `READY`、人工修正尚未完成或持久化失败时，不会把识别结果标记为已提交。Renderer 已提供完整重扫、行棋方选择、低置信度交叉点修正和安全提交入口。

自动化代码级回归覆盖识别领域规则、双帧融合、翻转方向、多候选拒绝、低置信度拒绝与修正、manifest/hash/class-map 校验、Worker 输出、超时/崩溃以及两阶段 Coordinator 状态。目前仓库**没有**满足本阶段验收要求的已验证 ONNX 权重、`manifest.json` 和 300 张独立完整棋盘测试集，因此不能声称 99.95% 单点准确率、99% 整盘准确率、100 次 DESYNC ≥99% 或 P95 <2 s 的现场/模型指标已经达标。`resources/recognition/` 已提供资源说明和 manifest 示例；在目标客户端/主题/DPI 上完成模型基准并锁定 ONNX Runtime 发行依赖后，才能关闭这些验收项。
