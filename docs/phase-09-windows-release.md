# 阶段 9：Windows 原生优化与发布

## 目标

在功能和可靠性已有量化证据后，完成 Windows 捕获与推理路径的必要优化、资源与数据库版本管理、进程故障恢复、安装包、升级和卸载，使普通用户无需配置开发环境即可安装运行。

优化必须以测量结果为依据。Windows.Graphics.Capture、DXGI、onnxruntime-node 或 C++/Rust 原生模块都不是默认必做项。

## 工具选择

- Electron Builder 或项目最终选定的 Electron 打包工具：生成签名安装包和便携测试包。
- Windows.Graphics.Capture：当阶段 0/6 证据表明现有截图在性能、遮挡或兼容性上不足时的首选原生捕获方案。
- DXGI Desktop Duplication：仅在 WGC 仍无法满足明确指标时评估。
- `onnxruntime-node`：优先替代 Python Recognition Worker 的发行路径；如兼容性不足，再把 Python Worker 独立冻结打包。
- Pikafish 多指令集二进制：根据 CPU 能力选择兼容版本，并提供最低兼容回退。
- SQLite migrations：安装、升级和回滚的数据兼容。
- Windows 虚拟机/干净物理机：安装、升级、卸载、高 DPI、多显示器和非管理员账户验收。

## 技术路线

1. 先在阶段 6 基准上记录 CPU、内存、捕获延迟、推理延迟、包体和启动时间，只优化超出预算的部分。
2. 若迁移到 WGC，保持 Window Capture 接口不变，用同一回放与实时测试对比正确性、延迟、遮挡、窗口移动和设备重置。
3. 若迁移到 `onnxruntime-node`，对全部独立测试集验证预处理、类别顺序、概率和最终布局与 Python 基准一致。
4. 为 Pikafish、ONNX 模型、Profile schema、数据库 schema 和应用建立独立版本与哈希清单。启动时先校验资源，再开放监控。
5. 打包时只包含运行所需资源，不包含训练数据、PyTorch、CUDA、Python 开发环境或未使用引擎二进制。
6. 建立首次启动、升级、数据库备份/迁移、迁移失败回滚、配置保留和卸载策略。卸载用户数据是否保留必须明确询问或在文档中说明。
7. 开启 Electron 安全基线：context isolation、受限 preload API、导航/新窗口拦截、本地资源路径校验和导入文件大小限制。
8. 在干净 Windows 10/11、非管理员账户、高 DPI、多显示器、断网和常见安全软件环境做安装与运行测试。
9. 生成日志与诊断包导出、隐私说明、已知限制、版本说明和回滚包。正式发布前完成代码签名；若尚无证书，只能标记为内部测试版。

## 交付物

- 性能基准与截图/推理路线决策记录。
- Windows 安装包、便携测试包和资源清单。
- 数据库迁移、备份和升级/回滚方案。
- CPU 兼容的 Pikafish 选择与模型完整性校验。
- 用户安装说明、已知限制、诊断导出和版本说明。
- 干净环境安装、升级、卸载和长稳报告。

## 验收标准

- 在支持矩阵内的干净 Windows 10/11 非管理员账户中，安装、首次启动、监控、分析和卸载全部成功；核心功能无需联网。
- 用户机器无需预装 Python、PyTorch、CUDA、Node.js 或编译工具链。
- 从上一正式测试版本升级 30 次，数据库迁移成功率 100%；故意制造迁移失败时可自动回滚并保留原数据。
- 在明确记录配置的基准测试机上，单客户端稳定监控时平均 CPU ≤ 10%、内存稳定在 500 MB 以内；若未达标，必须有测量证据、瓶颈说明和新的批准预算。
- 启动画面到可选择窗口 P95 < 3 s；画面稳定到局面更新 P95 继续满足阶段 3 的 500 ms 门槛。
- 连续运行 24 小时无主进程崩溃、无静默失步、无持续线性内存/句柄增长。
- Pikafish、模型或 Profile 资源损坏时启动校验能阻止不可信分析，并给出修复指引。
- 安装包若对外发布必须完成代码签名和签名验证；未签名构建只能作为明确标识的内部测试包。
