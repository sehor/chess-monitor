# 象棋监控分析软件开发计划

## 1. 文档说明

本目录把《象棋监控分析软件开发计划（重设计版）》拆分为可独立执行和验收的阶段文档，并吸收原始开发计划审查记录中的有效内容。

产品目标是在 Windows 10/11 上实现一个象棋实时监控分析软件：用户选定正在运行的象棋客户端并校准棋盘后，软件持续跟踪双方走子、同步内部局面，并调用 Pikafish 实时分析。

核心设计原则：

> 正常对局使用“Profile + 90 个交叉点图像变化 + 合法走法推导”，不逐帧运行完整视觉模型。ONNX 完整棋盘识别只用于首次连接未知局面、失步恢复和手动重同步。

本文档中的验收阈值是开发前的首版质量门槛。若实测后需要修改，必须在阶段开工前记录测试设备、数据集版本、修改原因和新阈值，不能在验收失败后临时降低标准。

## 2. 总体技术路线

```text
目标窗口
  → Window Capture
  → Profile 定位棋盘与 9×10 交叉点
  → 稳定帧与 ROI 图像变化检测
  → 上一局面 + 当前行棋方 + 合法走法枚举
  → 唯一候选走法 / 拒绝确认 / DESYNC
  → 更新 FEN 与棋谱
  → Pikafish 分析
  → Vue 界面显示评估、PV、箭头和历史曲线

首次未知局面或 DESYNC
  → 90 个交叉点 ROI
  → ONNX 15 类分类
  → 规则与置信度校验
  → 重建局面
  → 返回轻量跟踪
```

## 3. 统一技术决策

| 领域 | 选择 | 约束 |
|---|---|---|
| 桌面应用 | Electron + TypeScript + Vue 3 | Vue 界面视为重新实现；只复用开源项目中框架无关的逻辑 |
| 棋盘组件 | xiangqiground | 业务域统一使用 `red`/`black`，隔离组件内部 `white = red` 的命名 |
| 规则库 | `@west-shell/xiangqi.js`，锁定版本或 commit | 内部着法统一使用 ICCS 坐标格式，如 `h2e2`；正式开工前补齐规则兼容性测试 |
| 引擎 | Pikafish + 独立 Engine Manager | 进程、协议、超时、过期结果和崩溃恢复不得散落在 UI 中 |
| 图像处理 | `sharp` + TypedArray 像素差；必要时再加 SSIM | 所有棋盘采样均为 9×10 共 90 个交叉点 ROI，不称“90 格” |
| 完整识别 | `xiangqi-bot` 作为初始代码基础 + ONNX Runtime | 优先移植 ONNX 分类、校准、双帧和置信度逻辑；替换 macOS 平台代码；模型须针对目标客户端实测 |
| 训练 | Python + PyTorch，仅开发环境 | PyTorch、CUDA 和 Python 开发环境不进入最终用户安装包 |
| 数据 | SQLite | 保存设置、Profile、棋局、分析摘要、资源版本和迁移版本 |
| 截图 | 先用 Electron 可用能力完成验证，发布前评估 Windows.Graphics.Capture | DXGI 仅在量化性能或兼容性证据表明需要时引入 |

## 4. 模块边界

| 模块 | 责任 | 不负责 |
|---|---|---|
| Window Capture | 枚举窗口、抓取帧、记录时间戳和尺寸 | 判断走子 |
| Profile Manager | 窗口匹配、棋盘区域、方向、DPI、阈值和动画参数 | 推导局面 |
| Board Tracker | 变化检测、合法走法匹配、状态机、DESYNC | 引擎计算 |
| Recognition Worker | 未知局面和失步时的完整棋盘识别 | 正常逐帧跟踪 |
| Engine Manager | Pikafish 生命周期、命令队列、MultiPV、过期结果隔离 | UI 状态管理 |
| Persistence | SQLite、迁移、棋谱和诊断数据 | 业务规则 |
| Renderer | 棋盘、评估、PV、控制和错误提示 | 直接访问原生能力或子进程 |

Electron 必须保持 `contextIsolation: true`，Renderer 只能通过类型化 preload API 调用主进程能力。

## 6. 里程碑与依赖

- **可行性门（阶段 0）**：不通过就停止扩张范围，先解决抓屏、校准或变化检测。
- **分析底座（阶段 1–2）**：建立可独立测试的规则、引擎和 Profile 能力。
- **单客户端 MVP（阶段 3–4）**：正常对局无需完整模型即可持续跟踪和分析。
- **可靠版本（阶段 5–6）**：具备完整识别、拒绝错误、失步恢复、回放和长稳证据。
- **扩展版本（阶段 7–8）**：在稳定核心之上增加客户端和分析体验。
- **发行版（阶段 9）**：用户端不依赖 PyTorch、CUDA 或 Python 开发环境。

原则上按顺序执行。阶段 1 可在阶段 0 的抓屏实验进行时并行开发，但阶段 3 必须等待阶段 0–2 退出条件全部满足；阶段 7–8 不得阻塞单客户端 MVP。

## 7. 全局验收指标定义

| 指标 | 定义 |
|---|---|
| 棋盘定位成功率 | 能在允许误差内恢复 90 个交叉点坐标的测试次数 / 总测试次数 |
| 变化点召回率 | 实际应变化的起点、终点 ROI 被检测出的数量 / 实际变化 ROI 数量 |
| 确认着法准确率 | `MOVE_CONFIRMED` 中与标注棋谱一致的数量 / 全部已确认数量 |
| 拒绝率 | 因候选不唯一或置信度不足而未确认的走子数 / 实际走子数 |
| 漏着率 | 超过规定时间仍未确认或进入明确 DESYNC 的实际走子数 / 实际走子数 |
| 静默失步数 | 内部局面已错误但系统仍保持正常跟踪状态并继续分析的次数 |
| 重同步成功率 | 在超时内恢复到标注局面的次数 / 重同步尝试次数 |
| 更新延迟 P95 | 画面稳定到最新局面在 UI 可见的延迟 95 分位数 |
| 长期资源占用 | 指定测试设备上持续运行时 CPU、内存、句柄和子进程数量的趋势 |

每次验收必须保留：软件版本、Profile 版本、模型版本、测试设备、DPI、主题、原始截图或回放集、标注棋谱、指标报告和失败样本。

## 8. MVP 范围

MVP 必须支持：一个 Windows 象棋客户端、一个已验证主题、窗口选择、一次手动校准、Profile 持久化、双方走子跟踪、Pikafish 实时分析、无法判断时拒绝确认和手动重同步。

MVP 不包含：多客户端、自动通用棋盘定位、通用棋子模型、变化树、DXGI、C++/Rust 原生模块和用户端 PyTorch。
